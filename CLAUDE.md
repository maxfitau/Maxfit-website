## Client workout screen: three views (rebuilt 2026-11-07)

Max asked for the client workout logger (`workout/index.html`, `workout/app.js`, `workout/styles.css`) to be calmer and simpler, with three ways to see the same workout. Layout/UI only — the data side is unchanged.

- **Checklist (default), Show all, Simple view** — picked from the VIEW button (top right), remembered per member in `localStorage` under `maxfitWorkoutView|<id>`. All three are built from the same underlying set rows (`buildSetRow`); only the arrangement differs. Switching views never loses anything typed or saved — `snapshotRows_`/`applySnapshot_` carry over whatever's on screen, saved or not, when a view switch rebuilds the rows in the new layout.
- **Checklist:** one exercise (or superset) open at a time; finishing it collapses it and opens the next unfinished one automatically, scrolling to it. Others show as a single row (number badge, name, "2/3 sets · last 30kg × 8"). A superset's collapsed preview is its own small box (pill + A1/A2 names on a line) rather than a plain row.
- **Show all:** every exercise open, closest to the old single view. A sticky Set/Last time/Kg/Reps label bar sits once at the top instead of repeating per exercise.
- **Simple view:** the whole workout flattened into one ordered sequence of single sets (`buildSimpleSteps_`, reusing `supersetOrder_` for correct A1 → A2 → rest → round 2 ordering inside a superset) — one exercise, one set, one screen, with big ±64px steppers, a DONE button that saves and advances (its second line previews what's next), and Previous/Skip to navigate without saving.
- **The set row itself** (`buildSetRow`) has one DOM contract for all three views — `.workout__set`, weight/reps inputs, `row._saved`/`row._touched` — but two visual variants: `compact` (Checklist/Show all: SET | LAST TIME | KG | REPS | a round tick, no +/- steppers, numbers shown as placeholder text until confirmed) and `simple` (the big stepper cards, no tick — the page's own DONE button saves it). **Tapping the tick with nothing typed saves the grey suggested number shown as the placeholder**, not just whatever's literally in the box (`row._suggestedWeight`/`_suggestedReps`, read by `rowValues`) — this was the one real behaviour change from the old "always-prefilled" boxes and needs this fallback to still feel quick.
- **`allRows_(ctx)`** — every set row that exists right now, mounted or not, read from `ctx.items` rather than `els.list.querySelectorAll(...)`. Needed because Checklist only mounts the one open item's rows: a DOM-only scan (what `collectSets`, the Finish-tap sweep and the unsaved-entries check used to do) silently drops anything saved or typed in a collapsed item. All three now go through `allRows_`.
- **Finish Workout → review screen** (`showReview_`), not a direct send: TIME/SETS/KG LIFTED tiles, a "New Personal Best" card (heavier weight, or same top weight for more reps, than anything in that exercise's logged history — `allTimeBestSet_`; hidden, never guessed, if the sheet's columns can't be found), the muscles-worked figure + a plain per-muscle "N sets" list (computed once from the saved sets, not live), the "How did it feel?" note (moved here from mid-workout), the existing "already logged, will replace it" warning, and **Save & Close**, which is the old Log Workout send verbatim (same draft/offline/coach-mode/already-logged handling). "Back to workout" returns without sending and resumes the workout timer from where it was paused, not from zero.
- **Not built:** an actual video link for the "Watch how" play-icon button — it's wired up (`buildWatchButton_`) but hidden on every exercise today, since nothing in the Exercises tab carries a URL yet. No Sheet/Apps Script change was made for this; ask Max first if that's wanted.
- **Tested** in the browser against the real live sheet with `?id=maxfrench` (Max's own test card) — all three views, a superset, the review screen's PB/muscle calculations, and one real Save & Close. Two real bugs were found and fixed in the process: `ctx.collectSets`/`onFinishTapped_`/`hasUnsavedEntries` only reading DOM-mounted rows (see `allRows_` above), and the review screen's muscle bars being invisible (`<span>` fills need `display: block` for a `width` to do anything).
- **Deploy:** front-end only, no backend change. Cache tags bumped: `workout/app.js?v=20261107b`, `workout/styles.css?v=20261107a` (only loaded by `workout/index.html`, so no other page needed a bump).

## Boxing (built 2026-11-07, Code.gs 2026-11-07a, not live)

Timed boxing rounds — a bag/shadow-boxing block the client runs themselves, or pad work Max runs from his own phone in coach mode. A block is one exercise row in Workout Exercises (`Block Type` "Rounds"; blank is every normal exercise, unaffected); it can never join a superset.

- **Data:** Workout Exercises gained `Block Type`, `Work Seconds`, `Rest Seconds`, `Combos` (one combo per round joined by `" | "`, a single value means every round), `Run By` ("Client"/"Coach"), `Easier Option` ("Y"/blank) — added via the existing `ensureWorkoutExercisesColumns_`/`ensureColumns_` pattern, so old rows keep working untouched. Logged Sets gained `Duration (s)` and `Type` (blank = normal set, `"round"` = client-run round, `"pads"` = coach-run pad round); a round row always has Weight 0, Reps 0, Set Number = round number. **Heavy Bag, Shadow Boxing, Pad Work, Skipping** added to `EXERCISE_MUSCLE_DATA_` (Conditioning category, broad 14-key muscles, same call as the rest of that block — a punch combo isn't isolating one sub-region): Heavy Bag/Pad Work primary delts+obliques, secondary triceps/chest/abs(/calves on Heavy Bag only); Shadow Boxing the same minus chest; Skipping primary calves, secondary delts/forearms/abs. Run `seedExerciseMuscleData()` again to add them (safe to re-run, only fills blanks).
- **Everywhere that reads Logged Sets:** the muscle map (`workout/heatmap.js`) and weekly recap (`card/week.js`) skip `Type = "pads"`; a `"round"` row counts as a normal set once its exercise name resolves (Heavy Bag etc. now have muscle data) — effort scoring (`effortScaleForSet_`) was already a flat 1 regardless of weight, so a 0kg/0rep round already scored as a full set with no change needed there. `workout/progress.js` (Strength Progress, personal bests, "last time") already requires `reps > 0` to count a row, and a round's reps is always 0 — no code change needed, it excludes both kinds by construction. The review screen's own PB/muscle calculations (`computePersonalBests_`/`renderMuscleReview_`, `workout/app.js`) have the same explicit skip rules.
- **Client workout screen (`workout/app.js`), all three views:** a boxing block is its own item type (`buildBoxingItem_`) — "rows" are plain `{dataset, _saved, _duration, _type}` objects (not DOM nodes), going through the exact same `allRows_`/`collectSets`/draft/persist/postSession pipeline every normal set does (`ctx.saveRound`/`ctx.unsaveRound` are the round equivalent of `ctx.saveSet`). Checklist/Show all/the open Simple-view screen all render the same card (`renderBoxingCard_`): a BOXING/PADS tag, round boxes (tap to tick/un-tick by hand — logs the full Work Seconds), the combo list (`formatCombo_`: numbers joined "1 - 2 - 3", words "Jab · Cross · Lead hook" underneath; 1–6 map to Jab/Cross/Lead hook/Rear hook/Lead uppercut/Rear uppercut, anything else shown as typed), a shadow-boxing swap link (only when Easier Option is Y — renames the block's `activeName`, a live getter so every round's logged exercise name follows it), and a Start button. Simple view treats the whole block as **one step**, not one step per round (`buildSimpleSteps_`). A coach-run block shows only an info card on the CLIENT's own phone ("Pad work with Max" / done count) — Start only appears in coach mode.
- **Round timer** (`openRoundTimer_` + the `workout__timer-screen` overlay, shared by every view and both run-by kinds): wall-clock `endAt`-based countdown (not tick counting), a segment bar, a countdown ring, a combo card, Pause/End-round-early (logs the seconds actually elapsed), auto rest with ±15/skip, a bell (Web Audio, generated — no files) at 0 and a double-beep at 10s left, vibration, and the Wake Lock API while a round or rest is running. The coach variant adds a "COACH · PADS" tag, the client's name, the combo as large chips instead of the bold-line format, and a persistent "Finish & log to `<name>`'s card" button that saves whatever's done straight away (`coachFinishPads_`) and skips the review screen entirely — Max moving between clients doesn't need a muscle-map review of a session that was never his.
- **Workout builder (`workout/builder.js`/`.css`/`.html`):** "+ Add Boxing Rounds" opens a block editor dialog (exercise picker, Who runs it, Rounds/Work/Rest steppers, Same/Different-each-round combos with tap-to-insert chips, Easier option switch); a saved block is a compact summary row ("Heavy Bag · 3 × 2:00 · rest 1:00"), never expands inline, and is guarded out of ever joining a superset chain (`rowLinksToNext_`/`refreshSupersets_` both skip it explicitly, in either direction).
- **Session history (`workout/calendar.js`):** shows a boxing exercise's rows as "Heavy Bag · 3 rounds × 2:00" ("... with Max" for pads) instead of the usual per-set weight/reps list. Duration/Type are carried through `addSet`/`saveDay_` so editing one exercise on a day that also has boxing on it doesn't silently strip those columns back to blank when the day's whole session gets re-saved (`saveWorkoutSession` replaces the full day at once) — this was a real bug, found and fixed while building this.

## Fuel scope of practice (Max, 2026-10-29) — the rule behind all of Fuel

Max is a Cert IV personal trainer, not a dietitian. Fuel follows AUSactive / Dietitians Australia's "Nutrition advice within scope of practice": **the app tracks, informs and refers; the client makes their own choices.** Never build anything that:

- calculates personalised calorie or macro grams for someone (no BMR/TDEE calculators, no "your protein should be X g/kg"); clients type their own targets (`openTargets`, `MacroCore.checkTargets`, under 1,200 kcal refused with a GP / Accredited Practising Dietitian note), and the general AMDR ranges (NRV: protein 15–25%, fat 20–35%, carbs 45–65% of energy, `MacroCore.AMDR`) are shown as information only;
- writes a personalised meal plan or sizes portions to someone's targets (AI meal ideas and fridge ideas are general, at standard recipe serves; the client picks and chooses serves in the planner);
- recommends supplements, or gives advice for medical conditions, medications, pregnancy, allergies or intolerances, special diets (vegetarian/vegan/religious, low-carb, keto, fasting) or cutting out a food group: Food Q&A replies kindly that it can't help and points to their GP or an Accredited Practising Dietitian. Disordered eating gets a supportive reply, no numbers, GP + Butterfly Foundation (1800 33 4673).
- Max no longer sets targets on the coach page (`coachSetTargets` is retired). The scan prompts only estimate what's in the photo, never advise.
- Every Food Q&A answer and the planner carry "General guidance only. See a dietitian for a personalised plan." A first-open note ("Before you start", `maybeFirstOpen`) is saved as accepted in Members `disclaimer_accepted`.
- Supportive tone, never shaming. Run the coach page's **Food Q&A safety test** (20 out-of-bounds questions, `actionCoachSafetyTest_`) after any change to `CHAT_SYSTEM_PROMPT`.

## Stack

- **Front end:** static HTML, CSS and vanilla JS with no build step, no bundler and no npm. Each page loads its own `<script>` files. `card/sheet.js` holds the shared Sheet fetch and CSV parse helpers.
- **Hosting:** GitHub Pages from this repo, custom domain `maxfit.now` (see `CNAME`), HTTPS enforced. **The repo is public**, so secrets never go in any file here.
- **Backend:** one Google Apps Script web app (`apps-script/Code.gs`), deployed with "Anyone" access. Pages POST JSON to it as `text/plain` so the browser doesn't send a CORS preflight. Secrets live in Script Properties (`STAFF_PIN`, `GROCERY_CODE`).
- **Database:** a Google Sheet (`1dGQyIoJ2_XrkbvvPvM2JAY0xdeYQfsCnYHal8WZojUg`) shared as "Anyone with the link: Viewer". Pages **read it directly** as CSV (via `export?gid=` or `gviz?sheet=<name>`) and **write** through Apps Script. Because anyone can read that sheet, it must never hold private data such as food logs.
- **Member identity:** there is no login. Each member has a link like `maxfit.now/card/?id=<nameslug>`, where the slug is the lowercased name with non-alphanumerics stripped (`slugify()`). The id is saved in `localStorage` (`maxfitMemberId`) so the home-screen icon keeps working, and `app.js` rewrites the manifest's `start_url` for the same reason. Each member also has a random **Check-in Token**, which is encoded in the card's QR code. Both values can be read from the public sheet, so **neither one is a secret**.
- **Coach access:** gated by `STAFF_PIN` (see `checkPin_` in Code.gs), and used by `workout/builder.html` and check-in.
- **Timezone:** `Australia/Sydney` everywhere.

## Deploying

- **Front end:** Max pushes to GitHub himself because sessions have no push credentials. Bump the `?v=YYYYMMDDx` cache-busting tag on every CSS or JS file you change, in every page that loads that file, otherwise phones keep serving the old copy.
- **Apps Script:** pushing does **not** deploy it. Max pastes the code into the editor, saves, then goes to Deploy → **Manage deployments** → pencil → Version: *New version* → Deploy. **Never** choose "New deployment": that creates a new URL and orphans the URL hard-coded in the pages. Bump `BACKEND_VERSION` whenever the code changes. A GET on the web-app URL returns that version.
- **Live checks:** `curl -sL https://maxfit.now/card/index.html | grep -o 'app.js?v=[0-9a-z]*'`. Before assuming a schema, check the live sheet's headers with curl, because the live tabs have differed from what the code assumes.

## Macro tracker: phase plan

Build one phase at a time. **Stop after each phase for Max to test.** At the end of each phase: works on iPhone Safari and Android Chrome installed to the home screen, camera permission flows tested, 5 food photos + 5 barcodes + 1 fridge photo tested with JSON and screenshots shown, macro maths unit-tested, no API keys in client code, a clean console, this file updated, and a commit with a clear message.

1. **MVP:** daily targets (since 2026-10-29 the client types their own; see the scope rule above), photo scan, barcode scan (Open Food Facts), label-photo fallback, a confirm sheet with editable grams, daily totals (`128 / 180g`), edit and delete of entries, and recent + favourites.
2. **Smart suggestions:** a deterministic "what to eat next" ranking over a curated `foods` list (about 80 Australian staples, FSANZ values), plus an over-limit high-protein/low-calorie mode.
3. **Fridge scan:** photo → editable ingredient chips → 3 meals that fit the remaining macros → one-tap log.
4. **Motivation:** green days (protein at least 90% of target and kcal within ±10%), a 7-dot week, 5/7 counts as a win, "never miss twice", 5+ green days earns 1 punch on the loyalty card, milestones shown as red toasts, optional web push, and a coach dashboard.

### AI rules

- Claude API calls happen **server-side only**. The key is `ANTHROPIC_API_KEY`, kept in Script Properties or env and never in the repo.
- Use a Sonnet model with vision for photos, labels and fridge scans, and Haiku for text-only wording. Check current model IDs at docs.claude.com before changing them.
- Force structured output with tool use. Food schema: `{ items: [{ name, estimated_grams, kcal, protein_g, carbs_g, fat_g, confidence, notes }], meal_guess }`.
- Assume Australian portions, list oils and sauces as separate items, and prefer low confidence over invented detail.
- The browser resizes images to a 1024px long edge, JPEG at 0.8 quality. Photos aren't stored.
- Limit each member to 25 AI scans a day (a config value), use prompt caching on the system prompt, and log token usage and cost for every call.

### Maths

- Calories = 4P + 4C + 9F.
- Targets: the client's own numbers (`MacroCore.checkTargets`, 1,200 kcal minimum). No target calculator any more (removed 2026-10-29, scope of practice). `macroShares` shows their numbers as % of calories next to the NRV AMDR ranges.

### Guardrails

- Photo results show "Estimates only, typically within about 20% for photos". Barcode results show as exact.
- Settings carry a not-medical-advice line (GP / Accredited Practising Dietitian).
- A client sees only their own data. Only Max's coach access sees everyone.
